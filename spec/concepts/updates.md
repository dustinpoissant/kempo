# Updates

## Description
Kempo checks npm for a newer version of itself, tells the people who can install it, and installs it from the admin with nothing typed on the server: install, database migration, restart, wait for the server, reload. A site run from the Docker volume the init files set up stages the new version beside the running one and switches when the owner chooses; any other site installs in place.

## Dependencies
- [Notifications](../resources/notifications.md) — one per new version, and one per distinct database problem, linking to the Updates screen
- [Settings](../resources/settings.md) — `system:update_check_enabled`
- [Permissions](../resources/permissions.md) — `system:updates:manage`
- Scheduler — the `kempo:update-check` job, every 12 hours, registered by kempo at start
- [Database](db.md) — the `upgrade` table; `pg_dump` and `psql` in the image for backup and restore

## Context
A site installs kempo from npm and had no way to learn that a release exists or to take it without a shell on the server. The product goal is WordPress's ease: after the first setup, the owner (a baker with an online shop, not a developer) does everything with a button. Kempo is file-based, so the GUI edits the site's files directly, which is why the site's files have to live somewhere that survives replacing a container.

### Decisions
- **Core code is `node_modules`, the owner's stuff is everything else.** An update replaces only the code. `public/`, `templates/`, uploads and `.env` are the owner's and are never moved.
- **Docker: the volume is the site.** The image only seeds an empty volume (first start) and supplies the runtime; after that the volume (`/site/app`) is the site, so GUI edits, extension installs and updates survive a rebuilt or recreated container. The same shape as the official WordPress image. Rebuilding the image does not change a site that already has a volume.
- **Staged, not copied containers.** A literal copy of the container needs the Docker socket (root on the host) and loses edits made during the update. Instead the new version installs into `staging/` (a copy of `node_modules` plus the manifests) on the same volume while the site runs, so the site works until the switch and nothing the owner does meanwhile is lost.
- **The startup script does the switch, not the site.** `docker/entrypoint.mjs` (image-level, uses only Node) renames `app/node_modules` to `releases/` and the staged one into `app/` while nothing is running, so the site never loads files from two versions. Each step is repeatable, so a switch cut short finishes at the next start. Not symlinks: `npm install` replaces a symlinked `node_modules` with a real folder, which would break live extension installs.
- **A version proves itself.** `state/switch.json` is `requested`, `switching`, `switched`. A `switched` version that stops more than 3 times, or flags itself failed (a breaking data migration failed), is put back (code, replaced starter files, and the database when it changed data). The site clears the trial after a minute up. A manual rollback is never undone by itself.
- **Starter files by fingerprint, not a flag.** `.kempo/shipped.json` holds the SHA-256 of each file `init` copied (`app-public` into `public`, `app-templates` into `templates`). Equal to what was copied means never edited, so it updates; anything else is the owner's and is kept. Catches edits by any means, with no GUI code needing to remember a flag. A version can list `kempo.forceUpdate` paths it must replace (security): those need the owner's confirmation and are backed up first. A site with no record is judged against the running version's files. Extension email templates are not copied (a site file only exists once someone edits it and then wins), so they need no rule.
- **Kempo and extensions, from npm, together.** Extensions are npm packages, so each installed one is checked against the registry (`https://registry.npmjs.org` or `KEMPO_NPM_REGISTRY`) with the kempo check, and kempo and extensions are staged, switched and rolled back as one set in one `npm install`. An extension that needs a newer kempo (`peerDependencies.kempo`) is only offered together with it.
- **An extension's migration runs at start, not in the request.** `reconcileExtensions` compares each installed extension's version on disk with its row and, if newer, runs `upgradeExtension` (additive tables, `update.js`, newly declared permissions/settings/groups/hooks/widgets/jobs); older means the site went back (the row follows, no script). The row is claimed first (`UPDATE ... WHERE version = old`), so one of several starting servers does it; a failure restores the old version so it retries, and is reported. Extensions are taken in dependency order (their `dependencies`), so kempo-media's migration finds kempo-files current. This makes every route to a new version (switch, npm by hand, rebuilt image) behave the same, and replaces what a deploy script like ims's `update-extensions.mjs` did by hand.
- **Major means breaking for an extension, and so does a new minor while still 0.x.** `isBreakingBump`: every extension kempo has is 0.x, where the minor is the breaking step (npm's `^0.1.1` agrees). `update.js` is opaque, so a new breaking version, or `"breaking": true` in the new kempo-config.json, gets the breaking treatment (warning, backup, confirmation, restore on going back). A failed breaking extension upgrade flags the switch failed, like a failed kempo migration.
- **Extensions have no starter files.** Their `public/` is served from the package (`contentDirs`), so an update replaces it and nothing is copied into the site; owner changes live in the site and win (email overrides). The few that generate a file into the site (kempo-blog's template) use `writeSiteFile`, which applies the starter-file rule per extension (`.kempo/shipped/<name>.json`).
- **Never replace a link.** `npm install` over `npm run link:local` or a `file:` dependency discards the local checkout, so `getInstallInfo` refuses: the version is shown, the button is not.
- **Plain versions only.** `x.y.z` is the only thing that reaches `npm install`, which is what makes running it through a shell on Windows safe. No downgrades, no prereleases.
- **Peers move with it.** A peer (`kempo-server`, `kempo-ui`, `kempo-css`) below the new version's minimum is updated in the same install; one that already meets it is not touched.
- **One notification per version.** The job looks for `(kempo, update:<version>)` first, because raising a notification again re-opens it as unread for everyone.
- **The restart is the site's to choose.** `respawn` (a detached watcher waits for this process to exit, then starts the same command) for a hand-run server; `exit` (code 75, so `on-failure` policies restart it) under pm2, systemd, Kubernetes and Docker. `KEMPO_RESTART` overrides.
- **Additive sync first, migrations second.** `syncCoreSchema` runs at every start, before requests: it cuts from the schema snapshot everything the database lacks and asks drizzle-kit's `generateMigration` for the difference, so the result can only be additions and can never hold a DROP or TRUNCATE; a last `isAdditive` check refuses anything else. Not `drizzle-kit push`/`pushSchema`: push drops extension tables, and `pushSchema` drops its introspection parameters (it fails on a composite key and then calls `process.exit`) and proposes `TRUNCATE ... CASCADE` for a type change. A change the database refuses is reported (Updates screen, one notification per distinct problem) and the server starts anyway.
- **Data changes are migrations, and only majors may break.** `server/db/upgrades/*.js` (`meta`, `up`) run once in a transaction, recorded in `upgrade`; a first run baselines the files that already exist. A `breaking` one is read from the staged copy before the switch, so the owner is told; kempo backs the database up first with `pg_dump` (refusing if it cannot); a failure rolls back and restores the backup; going back past it restores that backup and loses later data, which the owner confirms. Minor and patch releases are additive-only by policy, so the previous version still runs on the updated database and going back loses nothing.
- **A new database sets itself up.** `seedIfNew` seeds groups, permissions and settings when there is no Administrators group, so an empty database plus `/setup` is the whole first-run.
- **The screen finds the new server by boot id.** Disk holds the new version before the old process stops, so the version cannot say which is answering; every process has its own boot id, read once at start. After the reload it compares the version it asked for with the one running, to tell an update from an automatic rollback.

## Implementation

### Location
`server/utils/updates/*` (`siteLayout.js` is dependency-free and copied into the image next to `docker/entrypoint.mjs`), `server/utils/setup/{syncCoreSchema,runUpgrades,seedIfNew}.js`, `server/db/upgrades/`, `docker/` (Dockerfile, compose, .dockerignore, entrypoint, copied by `npx kempo init`), `src/kempo/api/updates/**`, `src/admin/components/Updates.js`, `src/admin/updates/index.page.html`.

### Tests
`tests/extension-updates.node-test.js` (the npm check, reconcile at start, the checks before install, staged and in-place extension updates, the notification, `writeSiteFile`), `tests/updates.node-test.js` (registry, in-place install, peers, notification, a real respawn without a port), `tests/site-layout.node-test.js` (the layout, the startup script as a real process, the starter-file rules), `tests/release-updates.node-test.js` (prepare, confirm, switch, go back, data migrations, backup), `tests/schema-sync.node-test.js` (the additive sync, what it never touches, a refused change), `tests/http-contract.node-test.js` (permissions). Rehearsed in real Docker against a scratch database: first start from an empty database, live `npm install` in the volume, persistence across a replaced container, a switch, and the automatic rollback of a version that cannot start.
